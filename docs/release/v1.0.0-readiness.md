## Regression and integration evidence

Eight CTest suites: release_stress, mapper, config, settings, lifecycle, native_lifecycle, gui_smoke and tray_smoke. Final Release and Debug runs each passed 8/8, zero failures/skips. An earlier Debug run passed 7/8 with one GUI timeout; do not interpret final passing reruns as proof of deterministic GUI automation. The new deterministic stress suite exercises 100 runtime start/stop cycles and 100,000 synthetic snapshots with shared bindings, failed output callbacks, exact stable-state reconciliation and final release checks.

Tests cover analog boundaries/diagonals/opposites, simultaneous/shared mappings, disconnect/reconnect, disable/capture/save/reload/shutdown, failed key-down/up, corrupt configuration, concurrent stop/in-flight sampling and native instance IPC. GUI/tray suites open real windows/icons with mock output and temporary configurations: Save/Cancel, key selection/capture messages, background reopening, simulated session/power/TaskbarCreated and Exit during capture. They do not call SendInput or alter the user's actual configuration.

Read-only XInput sampling detected a connected controller. Physical button/trigger/stick acceptance, real injection into a target application, actual sleep/hibernate/lock, real Explorer restart, keyboard-only interaction, visual 100/125/150/200% DPI and screen-reader checks remain pending. Packaged executable extraction/hash/version are verified; first launch in a clean Windows user/VM with no developer tools and real user mapping remains pending. No such test is claimed from mocks.

## Performance and short stability

Four consecutive 60 s scenarios ran for approximately **240.14 s** in one engine-only Release probe; output was mocked even for real XInput sampling. This is a short stability observation, not multi-hour or overnight certification. The final LTO change affects only the application executable; probe/engine code was unchanged. Raw results are preserved in performance.txt alongside this report. Memory values describe the probe, not production tray use.

| Scenario | CPU % of one logical CPU | Working set | Private bytes | Poll p50 / p95 / max ms |
|---|---:|---:|---:|---|
| Synthetic connected | 0.156 | 4,673,536 | 983,040 | 15.494 / 16.277 / 17.252 |
| Disconnected | 0.052 | 4,710,400 | 1,015,808 | 262.729 / 264.864 / 266.106 |
| Disabled | 0.104 | 4,714,496 | 1,015,808 | 15.497 / 16.290 / 17.221 |
| Real XInput, output suppressed | 0.312 | 10,072,064 | 2,228,224 | 15.507 / 16.299 / 19.873 |

Synthetic sample-to-mock-output p50 0.0015 ms, p95 0.0046 ms. This excludes scheduling before sampling, SendInput and target consumption; it is not physical end-to-end latency. Requested polling was 4 ms (disconnected 250 ms); no timer-resolution change was made. CPU percentages divide process kernel+user time by elapsed time for one logical processor, not all 20; coarse Windows accounting affects short samples.

Synthetic scenarios returned to 54 handles and one thread after worker stop; active samples showed 55 handles/two threads after initial runtime initialization. Hardware initialization increased retained OS/XInput resources to 153 handles/five threads and ~2.18 MB private memory. This short sample cannot establish whether retained resources plateau; repeated sampling and overnight monitoring remain required. No sustained synthetic growth, crash or inconsistent mock key state was observed.

An additional final-build probe ran six consecutive ~5 s scenarios (30.21 s total), including three hardware sampling periods in the same process. After initial hardware initialization, stopped-worker counts held at 146 handles/six threads across all three periods, private memory ~2.16 MB. This supports short-term resource reuse, not a long-run leak conclusion. Raw final-probe results are retained as performance-repeat-final.txt in the source report directory; samples were taken while other verification work was running, so CPU figures are not isolated benchmarks.

The Release mock tray harness measured approximately 17–27 MB working set and 2.5–3.9 MB private memory in short connected/disconnected samples. Earlier phase-4 results are historical and use a different CRT. The ~10 MiB full-GUI resident target is not established. Full application CPU, long-run handle/thread trends and physical-input latency require further measurements.
